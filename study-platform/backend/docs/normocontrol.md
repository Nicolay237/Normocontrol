# Нормоконтроль

Материал, в котором студент проверяет работу на соответствие ГОСТ 7.32-2017 до
того, как понесёт её преподавателю.

Материал **советующий**: он ничего не запрещает и ни на что не влияет — ни на
сдачи лабораторных, ни на оценки. Отчёт нужен человеку, а не платформе.

## Кто что делает

Саму проверку выполняет **внешний сервис** — отдельный контейнер со своим
кодом, своей командой и своим циклом обновлений. Платформа про ГОСТ не знает
ничего: она держит очередь, кеш и историю.

Сервис поднимается рядом, **без выхода в сеть**, и наружу не публикуется:
он разбирает файлы, пришедшие от студентов, и лишних возможностей у него быть
не должно. Адрес задаётся `APP_NORMOCONTROL_BASE_URL`; пока он пуст, материал
честно показывает, что проверка недоступна, и файлов не принимает.

### Чего сейчас не хватает

**Версия с JSON-контрактом ещё не опубликована.** На `github.com/Nicolay237/Normocontrol`
лежит более ранняя: её `/api/check` отдаёт готовый HTML-фрагмент, а не JSON.
Платформа такой ответ считает несовместимым и отклонит каждую проверку кодом
`incompatible_report`.

Версия с `serialize_report`, React-интерфейсом и многостадийным Dockerfile
существует, но не закоммичена — она лежит только в рабочей копии. Пока её не
опубликуют, поднимать сервис незачем: `scripts/normocontrol-source.sh`
проверяет это и останавливается с объяснением, не доводя дело до сборки.

### Как поднять рядом

Сервис описан в `compose.yaml` под профилем `normocontrol`. Собирается прямо
из репозитория автора по закреплённому коммиту — копии у нас нет, и обновление
это осознанная смена ссылки, а не то, что случилось само.

Профиль намеренный: без него неудачная сборка чужого репозитория уронила бы
`docker compose up` целиком, а вместе с ним и платформу. Поэтому запуск в два
шага, и первый из них ничем не рискует.

**Шаг 1 — собрать и убедиться, что образ вообще собирается:**

```bash
docker compose --profile normocontrol build normocontrol
docker compose --profile normocontrol up -d normocontrol
docker compose exec backend python -c \
  "import urllib.request;print(urllib.request.urlopen('http://normocontrol:8080/health').read())"
```

**Шаг 2 — только после успешного первого:** прописать адрес в `.env`

```
APP_NORMOCONTROL_BASE_URL=http://normocontrol:8080
```

и добавить профиль в команду запуска (`run.sh`), чтобы сервис поднимался
вместе с остальными:

```bash
docker compose --profile normocontrol up
```

Сеть у него своя, с `internal: true` — маршрута наружу нет. Бэкенд подключён к
обоим сегментам, поэтому дотянуться до проверки может, а сама проверка в
интернет — нет. Портов наружу она не публикует. Проверено: своих сетевых
вызовов в сервисе нет ни одного, изоляция ему ничего не сломает.

Пока адрес в `.env` пуст, материал честно показывает, что проверка недоступна,
и файлов не принимает — платформа при этом работает как обычно.

## Порядок проверки

```js
// 1. Открыть проверку. Повторный вызов отдаёт уже открытую.
const run = await api.actions.normocontrol.run.create({ page_id });

// 2. Документ — в неё. resource_id это id проверки, не страницы.
//    POST /files/upload, multipart: upload, resource_type=normocontrol_run,
//    resource_id=<run.id>

// 3. Отправить в очередь.
await api.actions.normocontrol.run.submit({ run_id: run.id, file_id });

// 4. Отчёт приедет sync-событием normocontrol.run.changed.
```

Документ привязывается к проверке, а не к странице материала: вложение
страницы прочитал бы любой, у кого есть к ней доступ. Правило то же, что у
сдач лабораторных, и по той же причине.

**Документ удаляется сразу после проверки.** Отчёт остаётся навсегда, файл —
нет: это черновики, они и так есть у студента, а диск копить их незачем.

## Очередь

Проверка стостраничной работы занимает секунды и десятки секунд — это дольше
таймаута действия, поэтому отправка ставит работу в очередь и возвращается
сразу.

Очередь лежит в той же базе и разбирается фоновой задачей приложения.
Отдельный процесс ей не нужен: тяжёлый разбор идёт во внешнем сервисе, а наша
сторона только ждёт HTTP-ответа и event loop не занимает.

Что она гарантирует:

- **одна работа на пользователя за раз** — иначе человек с двумя десятками
  файлов занял бы очередь целиком;
- **потолок ожидающих работ** на пользователя: понятный отказ лучше растущего
  ожидания;
- **возврат зависших работ**: взятая упавшим процессом вернётся в очередь по
  истечении аренды;
- **повторы только там, где они осмысленны** — недоступность сервиса и таймаут
  повторяются, отказ по самому документу нет.

## Кеш по содержимому

Результат ключуется содержимым документа и версиями сервиса, а не файлом и не
пользователем:

```
(sha256 документа, версия чекера, версия схемы, версия норм)
```

По курсу ходит один методический шаблон: две сотни студентов приносят почти
одинаковые файлы, и считать одно и то же двести раз незачем. Совпавшее
содержимое отдаётся мгновенно и в очередь не попадает.

Отдавать чужой результат безопасно: отчёт — функция от содержимого, и у того,
кто принёс такой же файл, оно уже есть.

Версии в ключе решают и вопрос обновлений: вышла новая версия сервиса — кеш
промахивается сам, инвалидировать руками нечего.

## Обновления внешнего сервиса

Сервис дорабатывается постоянно, и проверок в нём будет становиться больше.
Интеграция построена так, чтобы это не требовало правок:

**Что проезжает само.** Новые категории замечаний, изменившиеся формулировки,
другое количество замечаний. Категории — обычные строки в ответе; ни
перечислений в коде, ни справочника в базе для них нет.

**Что сохраняется на будущее.** Ответ сервиса кладётся в базу **целиком**
(`raw`). Когда он начнёт присылать больше данных — например, привязку
замечания к странице, — историю можно будет перепроецировать, а не
пересчитывать: самих документов к тому времени уже не будет.

**Что мы проверяем.** Только конверт, на который опираемся:

```json
{ "categories": [ { "name": "...",
                    "issues": [ { "location": "...", "message": "..." } ] } ] }
```

Всё остальное — необязательно. `totalIssues` и `isClean` берутся из ответа, а
если их нет, считаются по замечаниям.

**Что останавливает обновление.** Пропавшее или переименованное поле конверта
и незнакомая мажорная `schemaVersion`. В обоих случаях проверка завершается
кодом `incompatible_report`, а не догадкой о том, что имел в виду сервис.

## Договорённость с сервисом

| Что | Зачем |
|---|---|
| `POST /api/check` синхронный | Очередь уже есть на нашей стороне; вторая дала бы двойное ожидание и непонятный статус |
| `schemaVersion` в ответе | Незнакомую версию честно отклонить, а не разбирать наугад |
| `GET /version` | Ключ кеша и подпись под отчётом |
| `categories[].issues[].{location, message}` не переименовывать | Единственное, на что мы опираемся |
| новые данные — необязательными полями | Добавление совместимо, переименование нет |

`GET /version` необязателен: пока его нет, версии пустые, и кеш работает по
одному лишь содержимому.

## Actions

| Action | Вход | Назначение |
|---|---|---|
| `normocontrol.open` | `{ page_id }` | Свои проверки для студента; все проверки материала для owner/editor/controller. |
| `normocontrol.run.create` | `{ page_id }` | Открыть проверку; повторный вызов отдаёт существующую. |
| `normocontrol.run.submit` | `{ run_id, file_id }` | Поставить документ в очередь. |
| `normocontrol.run.get` | `{ run_id }` | Одна проверка с отчётом. |
| `normocontrol.run.cancel` | `{ run_id }` | Снять свою проверку, пока её не взяли в работу. |
| `normocontrol.settings.get` | `{ page_id }` | Условие материала. |
| `normocontrol.settings.set` | `{ page_id, instructions?, accepting }` | Изменить; нужна роль editor и выше. |

Sync-событие `normocontrol.run.changed` приходит по области конкретной
проверки, а не материала: на странице сидят и другие студенты, и рассылать им
чужие отчёты незачем.

## Состояния проверки

```
draft ──submit──> queued ──> running ──> done
                    │            │
                    │            └──> failed
                    └──cancel──> cancelled
```

Коды отказа стабильны и не зависят от версии сервиса: `document_rejected`,
`unsupported_format`, `file_too_large`, `file_missing`, `timeout`,
`service_unavailable`, `incompatible_report`, `processing_error`. Текст
внешнего сервиса наружу не уходит — он меняется вместе с его версиями.

## Что нарочно не сделано

Проверка не влияет на сдачу лабораторной и не может её запретить: чекер
эвристический, и запирать студента за спорное замечание нельзя.

Git-сдачи не проверяются: снимок фиксирует commit, но файлов из репозитория не
выкачивает — клонирование вне текущего этапа (см. [source-control.md](source-control.md)).

Своих правил ГОСТа платформа не хранит и отчёты не редактирует.
